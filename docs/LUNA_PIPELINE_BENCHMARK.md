# Astra/low → Luna/max → Astra/low の比較

2026-09-09 JST。両方の構成を「Astra/lowの計画 → Luna/maxで実装 → Astra/lowでレビュー」に揃えた。両成果物は検証とレビューに合格したが、この1ペアではLocaloudの計画・実装・レビュー合計がCodex側の約3.02倍だった。

## 工程別の使用量

以下は入力（キャッシュ込み）＋出力のトークン数。出力の推論内訳は重複加算しない。

| 工程 | Codex native実装 | Localoud独立worker実装 |
|---|---:|---:|
| 共通計画：Astra/low | 97,149 | 97,149 |
| 実装：Luna/max | 444,659 | 1,603,921 |
| レビュー：Astra/low | 32,297 | 32,368 |
| 合計 | 574,105 | 1,733,438 |
| 合計のうち非キャッシュ入力 | 76,219 | 129,099 |

計画は[前回確定したAstra/lowの計画](evidence/luna-pipeline-benchmark-2026-09-09/PLAN.md)をそのまま共用した。新たに2回生成したものではなく、計画生成・保存の計測値を各構成に1回ずつ加算した参考合計である。この計画の計測範囲は1推論で、同じ推論の保存・fixture準備用ツール呼び出しも含む。実験準備全体や親による集計の使用量ではない。

## Luna/maxの実装部分

| 指標 | Codex native subagent | Localoud worker |
|---|---:|---:|
| 初回入力 | 39,620 | 27,204 |
| 累計入力 | 434,784 | 1,582,218 |
| うちキャッシュ済み入力 | 392,960 | 1,487,616 |
| 非キャッシュ入力 | 41,824 | 94,602 |
| 出力 | 9,875 | 21,703 |
| モデル呼び出し | 9回 | 26回 |
| 実行時間（概数） | 213.5秒 | 453.5秒 |

Localoudは初回入力が少なかったが、推論回数と後続コンテキストが増え、累計入力は約3.64倍になった。メモリ検索・追加ツール指示の確認・実装後の修正と再検証も含む。worker自身の進捗には、グループ管理を集合からリストへ変更した際の `.add` の残存を見つけ、`.append` へ修正してテストを再実行した記録がある。これらを集計から除外していない。

今回はLocaloudのキャッシュ率自体は高く、非キャッシュ入力の比率と総入力の比率は異なる。総トークンの差をそのまま課金額やサブスクリプション消費量の差に変換しない。

### 実行ログを追った追加診断

両方の最初の22テスト合格を境に分けると、入力は次のとおりだった。テスト合格後にも必要な確認はあるため、後半のすべてを不要なトークンとは扱わない。

| 入力の発生時点 | Codex native | Localoud |
|---|---:|---:|
| 最初の22テスト合格確認まで | 222,801 | 345,711 |
| その後、最終応答まで | 211,983 | 1,236,507 |

Localoud入力の78.15%は最初の合格確認後に発生した。具体的には次の行動が記録されている。

- 個人メモリの検索・再読、context-modeスキルとツールの探索、追加の指示ファイル取得。これらが自己完結した実装課題にも入り込んだ。
- 最初のunittest実行はcontext-mode経由で `(no output)` となり、stderrをstdoutへ寄せて再実行して初めて結果が表示された。
- ソース確認や後のテスト出力が検索用に格納され、指定intentに一致せず本文が返らない場面があった。後のテスト結果は別途検索して取得した。
- 追加の特殊な文字列サブクラス検証では `ModuleNotFoundError`、続く呼び出しでは改行のエスケープによる構文エラーが発生した。
- その後グループ管理の集合をリストへ変更し、`.add` を残したことで通常テストにエラーを生じさせ、さらに修正・再検証した。末尾改行や空白の確認も追加した。

この実験で揃えた計画・モデルだけでは、利用するツール、結果取得方法、workerの役割と終了条件まで制御できていない。今回の呼び出し回数の差は「必要な計画を渡して軽量に実装するworker」という狙いが実行時に保たれなかったことを示す。個々の追加行動と設定の因果関係を確定するには、worker専用の最小環境と明確な実装・レビューの責務で別の比較が必要であり、現時点で改善率は未測定である。

## 品質

両方とも以下に合格した。

- 固定テスト12件＋各workerの追加テスト10件、計22件。
- 共通の生成DAG検証1,000ケース（最大6ノード、並列数1・2・3・7）。全順列・実行可能部分集合・依存経路の列挙による照合と入力不変性の確認。
- 保護対象ファイルのハッシュ確認と、指定の2ファイルだけが変更されたことの確認。
- 別々のAstra/lowレビュー：両方 `pass`、具体的な指摘なし。

レビューは同じ評価基準、同じread-onlyのCodex app-server経路を使い、それぞれ新しいコンテキストで実施した。候補名と作業ディレクトリは中立名にし、実装元の名称や相手側の結果を渡していない。計画・契約・実装・テスト全文と、親が実行した検証結果を提示した。レビュー側でのコマンド実行はなく、判定は提供された証拠の範囲に限定される。レビュー後も対象ファイルのハッシュが一致することを確認した。

## 比較条件と限界

Codex側は実際の `spawn_agent` に `model=gpt-5.6-luna`、`reasoning_effort=max`、`fork_turns=1` を指定した。モデル指定時に全履歴forkを使えないため、計画を含む直近1ターンを継承した。Localoud側は本体の `CodexProvider::start_worker` と `start_turn_in_worktree` で同じ計画本文を渡した。モデル・思考量は両実装と両レビューの実行ログで確認した。

同じ依存関係スケジューラ課題、同じ計画・固定テスト、同じGitコミットから、実装のない新しい作業ディレクトリを作った。各実装は1体・1回で、worker内部の修正を含む全推論を保持した。Astraレビュー後の再実装は必要なかった。

1課題・1ペアのため一般的な優劣は確定しない。前回までの全履歴継承とはnative側の履歴条件も異なり、前回との差をモデル変更だけの効果とは評価できない。レビュー呼び出し経路は両方同じなので、native reviewerとLocaloud reviewerの起動方式の比較ではない。プラットフォーム内部のguardian、実験準備・親による検証・報告、ChatGPT利用量は集計対象外。UIのManifest取り込みからの全工程やセッション全体を測った結果ではない。
